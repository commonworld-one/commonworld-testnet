# Research directions and future CWN economy

This page records the project owner's product directions. A direction is not a deployment, a chosen design, or a partnership. Results below come from three dated sources, all on the current Commonworld Testnet (chain ID 11111327): operator runs of 20 November 2026 (agent authorization and Wave 1 checks, from the operator's reports), the project's public experiment series (https://commonworld.one/posts/238, 20 November 2026; 27 runs, roughly blocks 36,600-38,000), and fresh independent transactions of 21 November 2026. The contract scenarios used unaudited test contracts, and on-chain steps have mined receipts.

## Verified scenario results on the current chain

Everything in this section happened on the current chain, not on the earlier local chains. A scenario PASS means that exact scenario ran successfully with mined receipts; it is not network-level conformance certification. The runs covered at least the following scenarios:

- **EIP-712 (typed data signing): scenario PASS, several runs.** (1) Agent authorization (20 November): a custom `AgentAuthorization` contract `0x8ff338bc6202f39a2452f089c05b00a254e4631a`. The run's report describes checks of signature binding to chain ID and contract, agent registration, session-key rights, nonce, deadline, replay refusal and key revocation, with 10 included transactions: 8 successful and 2 expected refusals, all zero-fee. Four of these receipts were independently re-read on 21 November: a valid action with status 1 (block 28739), the two expected refusals with status 0 (blocks 28740 and 28742, replay and revoked-key refusals per the report) and the ERC-1271 action with status 1 (block 28745). The remaining counts are from the report, which also notes it did not isolate every limit and replay branch separately. (2) In the series, an EIP-712-signed attestation was accepted on-chain, submitted by a zero-balance relayer: tx `0x2fe57a3bbf1b4635a281c2ad5071ed7deafff71529c3e0343a50953dbb995b9e` (block 36736); a foreign signature reverted (`0x359ca643e7b33846974ee09ff2b1ee6de9260d0f481b6a8c21badd3fac57464a`, block 36737), a duplicate uid reverted (`0x2b80e992d72643d49713bfa115ba4b9dbea88ca9c78ae1615c233fa0aa7d8705`, block 36738), a non-author revoke reverted, the author's own revoke mined. (3) A locally computed userOpHash over the ERC-4337 EIP-712 domain matched the on-chain `getUserOpHash` exactly. Boundary: project-owned contracts; a working authorization prototype, not EAS compatibility, a standard marketplace or a wallet audit.
- **ERC-1271 (contract signatures): scenario PASS, limited.** A test smart wallet `0x6678a7c912eac4d70562851a7b81ded7ed23fa7d` verified an agent's contract signature and the action passed (block 28745, status 1); an invalid signature returns the invalid magic on `eth_call` (confirmed), and the run's report records the expected ERC-1271 magic value for the valid signature. Boundary: one test contract wallet, not a production wallet audit.
- **ERC-8004 Identity: PASS, Identity Registry only.** A registry proxy `0xd5d07bc50c219bd1de93f35f12e516172ed2ec57` registered one agent (ID 0): tx `0x302f4306c0ca5f33811d3fa7c30cbec6616e501b1104129aace2b7eb4784b143` (block 29647, status 1, zero fee); `ownerOf(0)` and the registration-v1 `tokenURI` are confirmed on-chain; the run's report also records wallet metadata and events. Full interface conformance is not claimed (a `supportsInterface` probe returned empty). Boundaries: ERC-8004 remains a Draft; the Reputation and Validation registries, reviews and full Draft compatibility were not tested; the proxy remains upgradeable with a test key.
- **ERC-20 / ERC-721 / ERC-1155 / ERC-165: scenario PASS.** Project-owned standard implementations (contract addresses in the public report): ERC-165 `supportsInterface` returned true for ERC721, ERC721Metadata, ERC1155 and ERC1155Metadata_URI (Enumerable intentionally omitted); canonical event topics matched; standard failure modes reverted. Boundary: no formal conformance suite was run.
- **ERC-4337 (account abstraction): prototype round trip PASS, overall PARTIAL.** Project-owned MiniEntryPoint `0xC2a96241625bC993a119cB386e6B2f934d3f14f7` and account `0xc7F0883Fbf9ce4dc009593c0A3b8E0e622D1Ff59` ran the full validate-then-execute round trip through `handleOps`, submitted by a zero-balance relayer (`0xe63e343e13f712c6cec26559e9ab5c987fe653505e2a1121c53e43f8a5cac1c8`, block 37932), with the exact `IAccount.validateUserOp` interface. Replaying the same UserOperation reverted (`0x16c36d0f8ad96b331bbcc6af2d2af8656d1bc91de21f5adeec081bb4661ab243`, block 37933); a foreign-signature UserOperation also reverted. Boundaries: the project's own MiniEntryPoint, not the canonical EntryPoint; the canonical stack (a production bundler such as Alto, Kernel accounts) was not part of any run on this network; the public RPC returned method-not-found for `eth_sendUserOperation` and `eth_supportedEntryPoints` at the time of the run, so compatibility with external ERC-4337 tooling is unproven.
- **EIP-7702 (set code / delegation): INCONCLUSIVE on the current chain.** Read-only probe only: a type-4 `eth_call` was accepted, but its empty result was identical to a plain call; no delegation was executed and no signed authorization persisted. The earlier type-4 test with actual setup ran on Mac Lab 2, not on this testnet (operator records). Support must not be claimed for the current chain.
- **x402 (HTTP 402 payment flow; not an EIP): flow shape covered.** The author's own facilitator and client ran x402Version 2 wire fields end to end: 402 challenge, on-chain payment (`0x3e1dc5b56edb9b5ebc9bd7524af8d781625ff3b785cf8e0bd4944dd71bdd8940`, block 37967, status 1), settlement (`0xae7e842955df66bfbf14838cb6cb1508eb2ac9f6e6e1965906585410f722916f`, block 37968, status 1), then 200; replay and wrong-key retries received 402 again. A separate earlier x402 mock was a local Lab-2 experiment (16 November). Boundary: no third-party x402 software involved; a shape, not certification.
- **EIP-155 / EIP-1559: PASS, from fresh independent transactions after the series.** A legacy transaction (`0xcc6cec1060abb1b4300c7bd39fce2b90b322c3ab261f0c33b82ebbc4a8f1729b`, block 39768) carried v = 11111327×2+35, direct proof of EIP-155 replay protection; a type-2 transaction (`0xa1dc2d3eac93560d1a4d10d7df0f1d540d223466bb8e1b0c8b321b827f174995`, block 39769) confirmed EIP-1559 envelopes. Both submitted on 21 November 2026.

Two further non-EIP scenarios from the series: session keys (a project-owned vault with on-chain grant, revoke, expiry and over-limit reverts; not an EIP) and a signed-intent account (an owner-signed intent relayed by a zero-balance relayer, `0xbf754a7b8ac62aba568b3ddbce13a685d7883a5c620d1dd33bd66094573e52d9`, block 37266, replay and wrong-signer reverted; a custom ecrecover scheme, not a standard).

Operator-run checks on 20 November (operator reports; receipts and contract code are on-chain):

- **RPC admission (reported, not independently reproduced):** per the operator's report, 8 signed self-transfers (4 via the public RPC, 4 via the operator's direct route) were all included and successful. This run proved the public route for simple signed transfers only; its scope did not cover public contract deployment or calls. The later experiment series (blocks 36,600-38,000) then proved public contract deployments and calls with mined receipts.
- **AMM smoke (reported, not independently reproduced):** two test ERC-20 (`0x47ceeca885936cfbaf770f712e17b5b2665bd6b1`, `0x356cde491e0546df82685dd96eb2e9f65c070319`) and a constant-product pool (`0x99c6ab66da4efd8230b77eea20af2ad8b0ff8bc4`) are deployed; per the run's report a swap passed with balances, reserves, supply and the invariant checked. Slippage and deadline checks were simulated, without a separate failing on-chain transaction.
- **Mock oracle and circuit breaker (reported, not independently reproduced):** the feed `0x4cdd7c0dfAECfCa67FCCF10E3A5bD38397969298` and consumer/breaker `0x4b129E4Cc108bfBEaE9D0A5279f5d8A6C1588293` are deployed; per the run's report, Healthy → Stale → Deviation → Unavailable → Healthy states passed, an unauthorized call was refused, and final recovery succeeded. This is the project's own mock feed, not a Chainlink feed.
- **Native tCWN distribution (reported, not independently reproduced):** 200 test addresses received 1 tCWN each; per the operator's records all 200 receipts succeeded with zero fee. A native-currency transfer, not ERC-20 and not an agent payment.

Not yet exercised on this network: the canonical ERC-4337 stack (Alto/Kernel), ERC-2771 (Lab 2 only), ERC-3009 and ERC-8183 payment flows, a real Chainlink feed, Hyperlane, Circle/CCTP and USDC.

## Oracles: Chainlink self-managed feeds (candidate)

In the series, freshness-checked reads of a mock price feed reverted on stale data; a public consumer-compatible live feed is not established on this network. The plan, a future add-on rather than a selected implementation, is Chainlink self-managed feeds, an official Chainlink Data Feeds model (https://docs.chain.link/data-feeds/self-managed-feeds): a Chainlink Runtime Environment workflow reads Data Streams and writes updates to a proxy contract that consumers read through the standard Data Feeds interfaces, while the chain or its designated operator runs the workflow and maintains the contracts. Chainlink Labs does not manage the onchain publication path, monitoring or service levels, and self-managed feed addresses are not in Chainlink's public catalogs. The reviewed materials do not establish a deployed self-managed feed on this network, Data Streams access, or any Chainlink integration or partnership.

## Payments: Circle and x402 (candidates)

The hypermarket direction keeps CWN as the place of choice, order, reputation and rewards, while settlement happens where the supplier already accepts payment. Circle was reviewed as a research candidate; the reviewed materials do not establish a confirmed official deployment, a Circle-issued asset, an endorsement or a partnership on this network. The x402 run described above used the author's own facilitator and client, so interoperability with real x402 software is unproven.

## Interoperability: Hyperlane (candidate)

The recorded plan is Hyperlane first between two local domains with a mock token, then a separate Sepolia test. The experiment series did not start it: connecting another network is a separate decision. The author-reported Base Sepolia bridge experiment is separate and has not been independently reproduced or security reviewed.

## Smart accounts: ERC-4337 (candidate)

The prototype round trip above shows the mechanics work on this network with project-owned contracts; production compatibility with the canonical EntryPoint and external bundlers is unproven. Smart accounts remain a candidate mechanism for embedded rewards without requiring a separate wallet.

## Future CWN economy, governance, DAO and The Network State

A direction from the original concept: platforms on the shared network could define their own economies (what citizenship gives, how rewards accrue, which services can be paid) through contracts and platform adapters. In the series, purchase rewards gated on a verified delivered receipt ran on the testnet, an early mechanics check for that direction. For governance, the project owner's public post (https://commonworld.one/posts/8, October 2026, quoting the October 2024 concept) describes a community of people and agents that might eventually finance projects through a DAO and, further down the road, experiment with network-state ideas. A public roadmap (https://commonworld.one/posts/38, October 2026) places this at a Shared ownership step, explicitly "a direction, not a promise of dates". The materials reviewed for this repository do not report a confirmed DAO deployment or a chosen governance model, rights design, tokenomics or legal structure. This page does not equate the DAO and The Network State, does not adopt any external doctrine, and claims no legal statehood.
